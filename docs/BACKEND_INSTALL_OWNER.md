# Backend install and owner sign-in (2026-10-13)

This is the one-page procedure that turns the SQL candidates into a live backend and
gives the owner a super-user (owner administrator) login. Everything below runs in
the owner's own Supabase dashboard; nothing here needs a secret in source control.

  (`https://gwcqlbjdvxebkxizfxsx.supabase.co`, ca-central-1). It was the unused,
  paused project in the account; it was restored on 2026-10-13 and found empty.
- Installed from this environment as migrations: candidates 1–3
  (`collaboration-watch.sql`, `room-invitations.sql`, `war-room.sql`) and the tables

## 1. Install the schema (SQL editor, about one minute)

1. Dashboard → **SQL Editor** → **New query**. Run this reset once so the bundle
   starts from a clean project (it removes only the partial install above; the
   project holds no other data):

   ```sql
   drop schema if exists sdi_private cascade;
   drop table if exists public.sdi_watch_sessions, public.sdi_room_members, public.sdi_rooms, public.sdi_watch_media cascade;
   delete from supabase_migrations.schema_migrations where name like 'sdi_%';
   ```

2. Open `backend/sql/dist/sdi-backend-install.sql` from the repository (41 candidates
   in README order, regenerated by `python3 scripts/backend/build_install_bundle.py`),
   paste the whole file into a new query and **Run**. Each candidate is its own
   transaction; if one fails, the ones before it stay installed and the error names
   the candidate. Expected result: no error, `sdi_private` schema plus the `public.sdi_*`
   functions and `public.users` exist.

3. Check: Dashboard → **Database → Functions** lists `sdi_admin_health`,
   `sdi_provision_owner`, `sdi_feed_action` and the others. Dashboard → **Advisors**
   should report no missing-RLS findings for `sdi_private` or `public.users`.

## 2. Owner account (already created 2026-10-13)

1. The owner account exists in the project: email `joewillisny@gmail.com`, handle
   `JWS`, email confirmed, password set privately by the owner. Nothing to do unless
   you want to change the password (Dashboard → Authentication → Users, or the
   command center's reset link). Only one account should ever hold the owner role.
2. Dashboard → **Authentication → URL Configuration**: add the address where you will
   open `website/admin.html` (the published review page, or `http://localhost` if you
   serve the folder locally) to **Redirect URLs** so password-reset links can return
   to the command center. Optional if you never use the reset link.

## 3. Enrol the second factor (command center, about two minutes)

1. Open `website/admin.html` (same copy that carries `admin-config.js`), sign in with
   the email and password from step 2.
2. The page detects that no authenticator is enrolled and shows **Enrol an
   authenticator**: scan the QR code (or type the secret) into Google Authenticator,
   1Password, Authy or similar, then enter the six-digit code. The backend marks the
   factor verified; the page then signs you in at MFA level 2 and shows
   "Signed in without administrator access" — expected until step 4.

## 4. Provision the owner role (SQL editor, ten seconds)

Run in the SQL editor (postgres role), replacing nothing but the handle if you want
another one; the subject is looked up from the email:

```sql
select public.sdi_provision_owner(
  (select id from auth.users where email = 'joewillisny@gmail.com'),
  'Joseph Willis', 'JWS');
```

Expected: `{"status":"provisioned","handle":"JWS"}`. The procedure refuses until the
email is confirmed and a verified factor exists, allows exactly one owner, writes an
audit row and ends every existing session of that account (sign in again).

## 5. Use the super-user login

- **Command center (web):** `website/admin.html` → sign in → authenticator code →
  every panel loads (health, configuration presence, users, approvals, moderation,
  publishing, support, finance, agents, agent proposals, announcements, marketing,
  policy versions), plus emergency stop and the proposal inbox decisions. Sensitive
  changes ask for a recent re-authentication (step-up).
- **Native admin (iOS):** the same account; the app needs its build settings
  `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` set to the values in
  `website/admin-config.js` (see `docs/AUTH_PROVIDER_CONFIGURATION.md`). Admin → Verify
  step-up uses the same authenticator.
- **Android:** the Android client is an offline source implementation; it carries the
  backend contract but no live connection yet (`docs/ANDROID_DELIVERY.md`).

The owner password is never in source, issues or chat. Additional administrators
are added by the owner from the native Admin → Users tab or `sdi_admin_permissions`,
each with MFA; member accounts sign up in the app and get a `public.users` row.

## Service workers (later)

Publishing, sweeps and the Spatter draft queue run from a host the owner controls with
`SDI_BACKEND_URL` and the project's service key from a secret store
(`docs/OPERATING_RUNBOOK.md`). They are not required for sign-in, Studio, Rooms, feed
reads or the command center's read panels.
